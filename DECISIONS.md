| 2026-10-06 | Sign-in is phone + 6-digit SMS code only; the API owns identity, sessions, consents, the role→permission map and match cases (migration 0003). | 2026-10-06 | Promo check (`POST /v1/promo/validate`) changes nothing; per-client throttle; ended/not-yet codes reveal no description; "already used" only for a signed-in customer (a stale token degrades to the anonymous check); purchase re-checks in NANO-06. | PROMO 06 without enumeration or launch leaks. | NANO-03, NANO-06 |
| 2026-10-06 | Ask us needs a signed-in customer, is throttled (5/min) and idempotent (client key → same reference). | SUP 05; the clinic must know who to reply to; no duplicate questions on retry. | NANO-03 |
| 2026-10-06 | Approved website photos are bundled and referenced by key until media storage exists. | D23; STF-36 media lands in NANO-07; rights R07 pending. | NANO-03, NANO-07 |
| 2026-10-06 | Hand-off booking: the API records a hand-off (idempotent per client key) after syncing existing Fresha bookings; the return check says "confirmed" only for a Fresha booking first seen after the hand-off and not already claimed by another hand-off (a basket treatment is preferred; one hand-off per booking, DB unique). Otherwise "checking" for 90 s from the first check (when the person is back) and then "not yet". With no Fresha read-back, or after the 24 h hand-off lifetime, it is "not yet". Fresha is read at most every 15 s per customer (in-process throttle) and a Fresha failure degrades to "not synced", never an error. | BOOK 16 truth-first; Fresha prefill and read-back are unconfirmed (E2) and no Fresha API is invented. | NANO-04 |
| 2026-10-06 | Fresha opens in the system in-app browser (`expo-web-browser`), not a WebView; on Android (where the call resolves when the Custom Tab opens) the app waits for its next return to the foreground before checking. | 2026-10-06 | Visits come only from the booking source (`visits` table filled by `FreshaGateway.readVisits`); status is shown as reported and never upgraded by the app. Sample Fresha bookings exist only with `DEV_SAMPLE_FRESHA` in local development. | BOOK 08/19; truth-first. | NANO-04 |
| 2026-10-06 | Late change/cancel requests go to a `visit_requests` queue: idempotent per client key (the app renews the key when the text or type changes), at most one open request per visit (DB partial unique index; a different type while one is open is refused with 409), approved requests stay in the staff list until marked done, transitions by `requests.manage` holders only, never on their own request, audited; customers are notified of approved/declined (with reason)/call needed. A request never changes the visit itself. | BOOK 18. | NANO-04 |
| 2026-10-06 | Notification hooks write to a `notifications` outbox (audience, template, data; staff notices target a permission, not a role). Delivery comes in NANO-09. | Keeps the lifecycle testable now without choosing a push/SMS vendor. | NANO-04, NANO-09 |
| 2026-10-06 | Catalogue services expose per-area pricing (`areas`: women/men sets, `maxAreasPerVisit`); the API validates hand-off areas against it. Basket visit limit 3 h is a client constant until the clinic sets a rule. | BOOK 17; BKG-10. | NANO-04 |
| 2026-10-06 | Visits are cached on the device for offline reading under `nano.private.*` (AsyncStorage), wiped on sign-out and session expiry; tokens stay in secure storage only. | VIS-01 offline state; SecureStore is too small for lists. | NANO-04 |
| 2026-10-06 | Mobile Jest runs with at most 2 workers. | Parallel workers ran out of memory on the low-memory build machine. | NANO-04 |
